## 테스트는 전부 통과했는데 첫 화면이 비어 있었다

학원 관리 서비스의 청구 기능을 만들 때의 일이다. 계획에 적은 항목을 전부 구현했고, 단위 테스트도 통과했고, 프론트와 백엔드 각각의 통합 테스트도 전부 초록불(`GREEN`)이었다. 나는 당연히 작업이 끝났다고 생각했다.

그런데 사용자가 목록 화면을 처음 열자 두 가지 문제가 동시에 터졌다. 최초에 해당 페이지에 접근할 때 작동해야 하는 요청은 `422(Unprocessable Entity)`로 실패했고, 생성되어 있어야 할 목록은 텅 비어 있었다.

원인은 둘 다 허무할 정도로 단순했다. 

첫 번째는 프론트엔드가 엔드포인트를 호출할 때 `billing_month`를 빈 문자열 기본값(`''`)으로 보내고 있었는데, 백엔드는 그 파라미터를 필수로 받도록 코드를 짠 것이다. AI 에이전트를 사용해 한 번에 큰 스콥을 개발하다 보면 종종 일어나는 일이다. 계획 단계에서 프론트와 백엔드의 파라미터 계약을 상호 대조하며 작업하지 않았던 것이 화근이었다.

두 번째는 더 기가 막혔다. "매월 1일에 청구서를 자동 생성한다"는 사양은 분명히 기획 문서에 적혀 있었다. 실제로 그 일을 수행하는 함수도 존재했다. 그런데 그 함수를 호출하는 코드가 **상세 화면에 진입했을 때 그 한 명에 대해서만** 작동하도록 연결되어 있었다. 일괄 목록을 보기 위해 들어온 사용자에게는 해당 로직이 전혀 트리거되지 않았던 것이다. 코드는 완벽하게 구현해놓고 정작 사용자가 원하는 기능은 동작하지 않는 참담한 상황이었다.

처음에는 통합 테스트를 더 촘촘히 작성하면 될 문제로 보였다. 그런데 다시 복기해보니 그게 아니었다. 두 사고 모두 **각자의 영역 안에서는 아무 잘못이 없었다.** 프론트 테스트는 프론트가 의도한 대로 동작하는지를 보았고 통과했다. 백엔드 테스트는 백엔드가 의도한 대로 동작하는지를 보았고 통과했다. 두 의도가 서로 어긋나 있었다는 것은 어느 쪽 테스트의 관심사도 아니었다.

빈 목록도 마찬가지다. 청구서를 만드는 함수는 잘 동작했다. 그 함수를 호출하는 상세 화면 경로도 잘 동작했다. **아무도 부르지 않는 경로가 존재한다**는 사실은 어떤 단위 테스트도 묻지 않는 질문이었다.

결국 이 둘은 코드 내부의 문제가 아니라 **경계의 문제**였다. 내 워크플로우가 놓치고 있던 것은 개별 코드가 아니라 코드와 코드 사이, 그리고 기획과 진입점 사이였다.

## 코드를 짜기 전에 사양부터 봉합한다

이 사고를 겪고 난 뒤, 엔드포인트가 바뀌는 작업이라면 **코드를 쓰기 전에** 계획 단계에서 표 세 개를 반드시 채우도록 워크플로우를 수정했다. 세 가지 표가 각각 위에서 겪은 결함을 하나씩 전담한다.

### 계약 표 (Contract Table)

프론트엔드의 기본값과 백엔드의 필수값을 나란히 비교한다. `422` 부류를 원천 차단하는 표다.

| 엔드포인트 | Query 키 | BE 필수? | FE default | 호환? |
|:---|:---|:---|:---|:---:|
| `GET /my/billing/list` | `billing_month` | ✓ 필수 | `filter.billing_month=''` | ❌ |
| `POST /my/discounts` | `name`, `type` | 모두 필수 | 폼 검증 통과 시만 전송 | ✅ |

### 셰이프 표 (Shape Table)

DB 컬럼에서 출발해 응답 DTO를 거쳐 프론트엔드 변환기에 닿기까지를 필드 단위로 추적한다. "백엔드에는 있는데 화면에서 `undefined`"가 뜨는 사고를 잡는다. 만약 DB 항목에 ❌가 쳐진다면 애초에 테이블 컬럼 자체가 없다는 뜻이므로, 마이그레이션이 이번 작업의 첫 단추가 되어야 한다는 명확한 신호가 된다.

| 필드 | DB | List 응답 | Detail 응답 | FE list | FE detail |
|:---|:---:|:---:|:---:|:---:|:---:|
| `students.payment_date` | ✓ | ❌ | ✓ | ❌ | ✓ |
| `homework.max_score` | ❌ | — | — | — | — |

### 트리거 표 (Trigger Table)

"매월 X", "자동 X" 같은 행위 사양마다 그 일을 책임지는 코드와, 그 코드가 **사용자의 자연스러운 진입점에서 실제로 닿는지**를 적는다. 빈 화면 사고를 잡는 표이며, 내가 겪은 두 번째 사고가 정확히 여기서 걸러진다.

| 행위 사양 | 책임 코드 | 호출 트리거 | 진입점 도달? |
|:---|:---|:---|:---:|
| 매월 1일 청구서 자동 생성 | `ensure_current_monthly_billing` | detail 진입 시 1명만 | ❌ |
| 학생·수업 변경 시 재계산 | `_recalculate` | discount apply API 내부 | ✅ |

그리고 타협 없는 규칙을 하나 걸었다. **표 안에 ❌가 한 줄이라도 남아 있으면 구현 단계에 진입하지 못한다.** 계획 시점에 해결하거나, 해결하지 못한다면 왜 미루는지를 구체적인 기술적 사유로 명시해야 한다. "나중에 검증", "지금 스코프 밖", "프론트는 다른 PR에서"는 사유로 인정하지 않는다. 바로 그 안일한 말들이 `422`와 빈 화면을 만들어낸 주범이었기 때문이다.

### 왜 문장이 아니라 표였나

같은 내용을 "프론트와 백엔드의 계약이 맞는지 확인할 것"처럼 문장으로 적을 수도 있었다. 실제로 처음에는 체크리스트 문장으로 적어두었다.

하지만 문장은 모호하고, 에이전트나 개발자나 적당한 이유를 대며 얼렁뚱땅 넘어가기 일쑤다. 반면 표는 칸이 비면 비어 있다는 사실이 시각적으로 즉각 드러난다. 칸을 채우려면 양쪽 코드를 실제로 열어봐야 하고, 그 순간 프론트의 기본값과 백엔드의 필수 여부가 **강제로 한 줄에 나란히 놓인다.** 표는 단순한 검사지가 아니라 **각자의 영역만 보던 시선을 강제로 경계선 위에 올려놓는 장치**다.

여기에 더해 계획 단계의 순서도 뒤집었다. 처음에는 "무엇이 변하는가" 가설을 먼저 적고 코드를 뒤지게 했더니, 에이전트가 내 가설에 들어맞는 코드만 찾아오는 확증 편향이 발생했다. 그래서 코드베이스를 먼저 객관적으로 훑게 한 뒤, 그 탐색 결과를 근거로 변화 요인을 적도록 순서를 바꿨다. 문장 하나 순서를 바꿨을 뿐인데 판단의 성격이 '가설'에서 '사실'로 바뀌었다.

## 실행 사이클 안쪽을 지키는 두 개의 방패

계획 단계에서 사양의 구멍을 꿰맸다면, 이제 실제로 코드를 짜는 `RED-GREEN-REFACTOR` 사이클 안쪽을 지켜야 했다. 여기서도 실전의 압력으로 두 가지 장치가 생겨났다.

### 테스트 기준선 (Baseline)

여러 세션을 병렬로 돌리거나 작업이 길어지다 보면, "지금 발생한 `RED`가 내가 방금 작성한 테스트 때문인가, 아니면 원래 깨져 있던 것인가?"가 모호해지는 순간이 온다. 에이전트가 기존 실패를 조사하느라 토큰과 시간을 낭비하는 것을 막기 위해, 사이클 착수 직전 전체 테스트를 돌려 실패 목록을 계획서에 박아두었다.

```text
### Test Baseline
- 등록일: 2026-04-14
- 기존 실패: 5건 (이번 작업과 무관)
- 실패 목록: test_a, test_b, test_c, test_d, test_e
```

단계가 끝날 때마다 이 베이스라인과 대조한다. 전체가 초록불(`ALL GREEN`)이 아니더라도 신규 실패가 0건이면 통과한다. "이 실패가 내 것인가"를 즉시 판정해주는 장치다.

### 거짓 GREEN (False Green) 방지

더 치명적인 문제는 **거짓 GREEN**이었다. AI에게 테스트를 통과시키라고 지시하면 가장 쉬운 지름길을 택한다. 바로 **의존성을 전부 Mock으로 덮어버리는 것**이다.

반환값을 하드코딩한 `Mock`으로 감싸면 테스트는 무조건 초록불이 된다. 하지만 정작 실제 코드가 깨져도 테스트는 절대 실패하지 않는다. 테스트 스위트는 풍성한데 결함은 하나도 잡아내지 못하는, '테스트가 아예 없는 것보다 더 위험한 상태'가 된다.

Kent Beck은 유효한 테스트를 다음과 같이 정의했다:

> **행동이 바뀌면 반드시 실패하고(Behavioral), 구조만 바뀌면 깨지지 않는다(Structure-insensitive).**

이 원칙을 지키기 위해, 테스트 작성 직후(`RED` 단계)에 통과해야 하는 검증 체크리스트를 실행 루프에 심었다:

- [ ] 테스트 대상이 단순 CRUD 같은 얇은 래퍼인가? → 단위 테스트 부적합. 통합 체크로 이관
- [ ] Mock 설정값을 그대로 꺼내 단언(assert)하고 있는가? → 동어반복. 삭제 또는 재설계
- [ ] 내부 메서드의 호출 횟수·순서를 검증하는가? → 화이트박스 테스트. 행위 결과 검증으로 전환
- [ ] Query 의존성에 Mock을 썼는가? → Stub/Fake로 교체
- [ ] Command 의존성에 Stub을 썼는가? → Mock/Spy로 교체
- [ ] 내부 도메인 객체를 대역으로 만들었는가? → 시스템 경계(외부 IO)만 대역 사용
- [ ] 생성자 테스트에서 정상 케이스(happy path)를 검증하는가? → 금지. 실패 케이스(`pytest.raises`)만 작성

계획 단계가 "어디에 테스트를 배치할 것인가"를 정하는 의도라면, 이 체크리스트는 **"방금 짠 테스트가 진짜 유효한가"**를 걸러내는 실행 게이트다.

## 수집하고, 계산하고, 다시 내보낸다 (IO-Pure-IO)

테스트를 통과시키는 최소한의 코드를 작성하는 `GREEN` 단계에서도 중요한 구조적 강제가 필요했다.

유명 오픈소스 `FastAPI` 프로젝트들(`Polar`, `Mealie`, `Onyx`, `Open WebUI` 등)을 뜯어보면서 발견한 공통된 패턴이 있었다. 뛰어난 코드베이스일수록 서비스 메서드가 언제나 일정한 3단계 리듬을 유지하고 있었다:

```python
async def generate_report(self, student_id: int) -> Report:
    # 1. 수집 — IO (DB 조회, 외부 API 호출)
    raw_data = await self.crud.get_student_data(student_id)
    config = await self.crud.get_org_config(self.org_id)

    # 2. 계산 및 변환 — Pure (순수 비즈니스 로직)
    structured = structure_student_data(raw_data)
    report = build_report(structured, config.template)

    # 3. 실행 및 저장 — IO (DB 저장, 알림 발송)
    await self.crud.save_report(report)
    return report
```

나는 이것을 **IO-Pure-IO**라고 불렀다.

계산 로직이 DB 호출이나 외부 통신과 한 줄에 뒤섞여 있으면, 비즈니스 로직 하나를 검증하겠다고 매번 DB를 띄우고 네트워크를 타야 한다. 규칙 변형이 5개면 무거운 통합 테스트가 5개로 불어난다. 테스트가 50초씩 걸리는 비극은 여기서 시작된다.

`GREEN` 단계에서 요구하는 규칙은 단순하다. **수집(IO)·변환(Pure)·실행(IO)을 한데 뒤섞지 않는다.** 순서만 지켜두면 `REFACTOR` 단계에서 순수 함수를 뽑아내는 것은 기계적인 일이 된다.

나중에 알게 된 사실이지만, 이 구조는 Gary Bernhardt가 2012년에 발표한 **Functional Core, Imperative Shell (함수형 코어, 명령형 껍데기)**과 정확히 일치하는 개념이었다. 개념을 먼저 배워서 적용한 것이 아니라, 현장의 병목을 해결하려다 오픈소스의 패턴에서 만나고 사후에 이론적 이름을 확인한 셈이다.

## 합격률 100%의 검토자를 해고했습니다

하지만 진짜 최종 보스는 따로 있었다.

아무리 계획을 촘촘히 세우고 실행 체크리스트를 심어도, `REFACTOR` 단계에서 AI 에이전트에게 "객체 설계 규칙을 위반했는지 스스로 검토하라"고 시키면 위반 사항이 거의 나오지 않았다. 언제나 만점, **합격률 100%**였다.

이유는 단순했다. **방금 그 코드를 짠 놈이 검토까지 하고 있었기 때문이다.** 자신이 왜 그렇게 코드를 작성했는지 전후 맥락과 고충을 훤히 알고 있는 상태에서는, 규칙 위반을 마주해도 "이건 이런 사정이 있으니 합리적인 예외다"라며 스스로에게 관대해진다. 인간 개발자가 자기가 쓴 글의 오타를 못 찾는 것과 똑같은 확증 편향이다.

### Coordinator 패턴과 맥락 없는 검토자

2026년 4월 유출된 클로드 코드 소스코드 안에서 나는 해답의 실마리를 찾았다. 거기에는 비공개 상태였던 `Coordinator`(조정자) 아키텍처가 들어 있었다.

시스템 프롬프트에 적힌 문장들이 큰 충격을 주었다:
- `Read-only tasks: Run in parallel freely` (읽기 작업은 자유롭게 병렬 실행하라)
- `You are a forked worker process. Stay strictly within your directive's scope.` (너는 메인 에이전트가 아니다. 지시받은 범위에만 머물러라)
- `Coordinator MUST read and synthesize findings. Never delegate understanding.` (**이해를 위임하지 말라.**)

나는 이 구조를 TDD 워크플로우의 역할 분리로 즉시 이식했다:

| 역할 | 담당 에이전트 | 핵심 규약 |
|:---|:---|:---|
| **탐색자 (Research)** | 읽기 전용 서브 에이전트 | 코드베이스 탐색, 기존 테스트 영향 분석 |
| **설계자 (Synthesis)** | 메인 에이전트 | 탐색 결과를 종합하여 계획 및 설계 수립 |
| **구현자 (Implementation)** | 실행 에이전트 | 계획을 바탕으로 `RED` ➔ `GREEN` 사이클 수행 |
| **검토자 (Verification)** | **독립 서브 에이전트** | **맥락을 모르는 상태에서 코드와 규칙만 대조** |

가장 핵심적인 조치는 **검토자에게 구현자의 대화 맥락을 전혀 물려주지 않는 것**이었다. 

검토자는 구현자가 어떤 시행착오를 겪었는지, 무슨 변명을 하고 싶은지 모른다. 검토자에게 주어지는 프롬프트의 첫 줄은 이렇다:

> "당신은 엄격한 코드 검토자다. 구현자의 의도나 개발 맥락은 모른다. 오직 작성된 코드와 전달된 설계 규칙만 대조하여 위반을 보고하라."

심지어 어떤 파일이 서비스인지 값 객체인지 분류하는 작업조차 검토자가 직접 판정하게 했다. 구현자가 "이건 그냥 유틸리티 파일이야"라고 밑밥을 깔지 못하도록 하기 위해서였다.

자가 검토자를 해고하고 낯선 검토자를 세우자, 숨어 있던 위반들이 쏟아져 나오기 시작했다.

### 유예 정책과 최종 재대조

쏟아지는 위반을 통제하기 위해 엄격한 유예 기준을 세웠다.
- 치명·높음·중간 등급: 예외 없이 즉시 수정.
- 낮음 등급: 구조적 한계라는 명확한 근거가 있을 때만 계획서 하단에 유예 사유를 적고 통과.
- **"지금 스코프가 아니라서"는 절대 유예 사유로 인정하지 않는다.** (3번의 422 사고를 일으킨 주범이었기 때문)
- 같은 규칙 위반이 3회 이상 누적되면 구현자의 부주의가 아니라 설계 자체의 결함으로 간주하고 설계를 다시 검토한다.

그리고 모든 작업이 끝나면, 구현 시작 전에 작성했던 **봉합 표 3종(계약·셰이프·트리거)**을 실제 생성된 코드와 최종 재대조한다. 계획에서 ✅였던 항목이 코드에서도 여전히 ✅인지 확인하고, ❌가 단 하나라도 남아 있으면 머지 게이트를 통과할 수 없다.

## 이제 코드 밖을 볼 시간이다

TDD를 처음 시작했을 때 내 목표는 "AI가 헛소리하지 않고 제대로 된 코드를 짜게 만드는 것"이었다.

하지만 현장에서 겪은 수많은 사고와 배신은 내게 다른 진실을 가르쳐주었다.
- 단위 테스트가 다 돌아도 진입점과 사양이 어긋나면 화면은 하얗게 비고,
- 규칙을 정해두어도 실행 루프에서 통과하는 척하는 거짓 초록불이 생겨나며,
- 자기가 짠 코드를 자기가 검토하는 한 품질은 절대로 보장되지 않는다.

사양 봉합 표 3종, 테스트 기준선, 거짓 `GREEN` 방지 체크리스트, `IO-Pure-IO` 분리, 그리고 맥락 없는 독립 검토자까지. 이 모든 장치들이 맞물리고 나서야, 비로소 나는 단 한 명의 AI 에이전트와 페어링하여 완벽하게 신뢰할 수 있는 프로덕션 코드를 뽑아내는 **'단일 세션 TDD 품질 엔진'**을 완성할 수 있었다.

**하지만 이 완성이 또 다른 갈증의 시작이었다.**

품질 엔진이 단단해질수록 기능 개발, 결함 수정, 마이그레이션 등 쏟아지는 요구사항의 속도를 따라잡아야 했다. 하지만 에이전트 단 한 놈만 데리고 한 땀 한 땀 TDD를 돌리기에는 현실의 시간이 턱없이 부족했다. 그렇다고 하나의 브랜치에서 터미널 창을 여러 개 띄워 다중 에이전트를 돌리자, 서로의 코드를 덮어쓰고 남의 테스트 실패를 디버깅하는 난장판이 벌어졌다.

다음 글에서는 시선을 단일 세션에서 '다중 에이전트 병렬 오케스트레이션'으로 넓혀보려 한다. 에이전트마다 독립된 물리적 방(Git Worktree)을 배정하고 `cmux`로 여러 에이전트를 동시에 지휘하며 2주 만에 475개의 커밋을 쏟아낸 실전 병렬 협업기를 이야기하겠다.
