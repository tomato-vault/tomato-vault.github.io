## 1. 죽은 지식과 살아있는 원칙: 왜 기술 노트는 낡는가

수많은 주니어 개발자들의 노트 앱에는 다음과 같은 문서들이 가득하다:
* `Docker 명령어 모음.md`
* `PostgreSQL 트랜잭션 격리 수준 요약.md`
* `React useEffect 동작 원리.md`

나 역시 처음에는 이런 식의 '요약 노트'를 수백 개 작성했다. 책을 읽고 중요한 문장을 밑줄 치고 마크다운으로 깔끔하게 옮겨 적었다. 

하지만 실제 프로덕션 장애가 터졌을 때, 이 노트들은 철저하게 무용지물이었다.
금요일 밤, 배포 후 데이터베이스 커넥션 풀이 고갈되고 API 응답이 504 타임아웃을 뿜어낼 때, "PostgreSQL에는 Read Committed, Repeatable Read, Serializable이 있다"는 교과서적 설명은 아무런 해결책을 주지 못했다.

정작 필요한 것은 **"커넥션을 물고 외부 API를 호출하지 마라"**, **"Slow Query 발생 시 인덱스보다 Rows Removed by Filter를 먼저 보라"**는 구체적이고 단호한 **행동 원칙(Actionable Principle)**이었다.

지식은 단일한 덩어리가 아니다. 그것이 세상의 객관적 사실인지, 내가 일하는 방식인지, 아니면 위기 상황에서 지켜야 할 철칙인지에 따라 존재하는 층위가 완전히 달라야 한다.

## 2. 지식의 세 층위: 백과사전, 작업대, 그리고 캡스톤

Vault OS는 200번 개발 지식 공간을 세 개의 명확한 계층으로 수직 분할했다:

```mermaid
flowchart TD
    subgraph L3 ["제3층: 지식의 캡스톤 (Capstone)"]
        PR["299 Principles<br/>(타협할 수 없는 60개 실천 원칙)<br/>* 평균 24.3회 수정 실측"]
    end

    subgraph L2 ["제2층: 나만의 작업대 (Workbench)"]
        OPS["210 Ops / AI-Ops<br/>(에이전트 오케스트레이션, 쉘 스크립트, 워크플로우)"]
    end

    subgraph L1 ["제1층: 보편적 백과사전 (Encyclopedia)"]
        KB["200 Dev KB (201 CS ~ 209 Language)<br/>(공식 문서, 언어 문법, 아키텍처 이론)"]
    end

    L1 -->|실전 적용 & 검증| L2
    L2 -->|장애·사건(Case) 피드백| L3
    L3 -.->|판단 기준 강제| L2
```

### 제1층: 200 Dev KB (보편적 백과사전)
- **성격**: 세상에 이미 존재하는 객관적 기술 사실. 내가 발명한 것이 아니라 인류가 합의한 컴퓨터 과학과 소프트웨어 공학의 정석.
- **분류 체계**: `201 CS`, `202 Database`, `203 Backend`, `204 Frontend`, `205 Infra`, `206 Mobile`, `208 Architecture`, `209 Language`.
- **원칙**: 주관적 감상을 섞지 않고 객관적 정의, 동작 메커니즘, 표준 다이어그램을 보존한다.

### 제2층: 210 Ops (나만의 작업대)
- **성격**: 보편 지식을 내 컴퓨터 환경에서 실제로 구동하기 위한 도구와 작업 프로토콜.
- **주요 내용**: `cmux` 병렬 워크트리 운영법, `vault` CLI 스펙, AI 에이전트 발주 규약, 도커 컨테이너 격리 쉘 스크립트.
- **원칙**: 내 손에 익은 도구들의 사용법이자, 나와 AI 에이전트가 함께 일하는 작업대.

### 제3층: 299 Principles (지식의 캡스톤)
- **성격**: 숱한 실패와 실전 프로젝트를 거치며 정립한 **"무슨 일이 있어도 결코 어겨서는 안 되는 실천 원칙"**.
- **도메인**: Backend, Database, DevOps, Frontend, Mobile, Software Design 6개 분야 총 60여 개 원칙.
- **특징**: "모든 원칙은 실제 장애 사건(`case` 문서)에서 태어난다."

## 3. 실측 24.3회 수정의 법칙: 장애에서 태어난 원칙만 살아남는다

2026년 1분기 Vault 진단 보고서를 분석하던 중, 매우 흥미로운 실측 통계가 발견되었다.

* 일반적인 `200 Dev KB` 기술 노트는 평균 수정 횟수가 **1.8회**에 불과했다. (작성 후 거의 다시 열어보지 않음)
* 반면, `299 Principles`에 등재된 원칙 문서들은 평균 수정 횟수가 무려 **24.3회**에 달했다.

왜 이런 극단적인 차이가 발생했을까?

원칙 문서는 책상머리에서 단번에 완성되는 글이 아니기 때문이다.
예를 들어 `299 Principles/Database/쿼리 튜닝 대상은 Rows Removed by Filter 최소화를 목표로 하라.md`라는 문서를 보자:

1. **v1 (최초 작성)**: "WHERE 절에 인덱스를 잘 걸자"는 막연한 교과서 지식으로 시작했다.
2. **v2 (장애 발생)**: 복합 인덱스를 걸었는데도 Slow Query가 터지며 커넥션이 폭발했다. `EXPLAIN ANALYZE`를 열어보고 나서야 인덱스 스캔 후 필터 단계에서 10만 건이 버려지고 있었다는 사실을 발견하고 "Rows Removed by Filter"라는 지표를 기록했다.
3. **v5 (AI 협업)**: AI 에이전트에게 쿼리 최적화를 맡겼더니 자꾸 불필요한 서브쿼리를 덕지덕지 붙이는 실수를 반복했다. 에이전트가 쿼리를 작성할 때 강제해야 할 평가 기준으로 이 원칙을 개정했다.
4. **v12 (실전 교훈)**: 대규모 배치 작업에서 페이징 쿼리를 짤 때 No-Offset 커서 기반 페이징과 결합하는 세부 규칙이 덧붙여졌다.

이처럼 **원칙은 수많은 프로젝트 사건(Case)을 온몸으로 받아내며 20번 넘게 부서지고 다시 쓰인 생존의 기록**이다.
이런 원칙만이 나와 AI 에이전트의 손가락을 지배하는 살아있는 무기가 된다.

## 4. 지식의 감가상각과 퇴역(Deprecation)

소프트웨어에 레거시 코드가 쌓이듯, 지식베이스에도 반드시 유통기한이 지난 낡은 지식이 쌓인다. 3년 전 FastAPI 0.68 버전의 팁이나 Webpack 4 설정법은 오늘날 아무런 가치가 없을뿐더러, AI에게 잘못된 컨텍스트를 주입하는 독약이 된다.

Vault OS는 지식의 퇴역을 다음 프로토콜로 관리한다:

1. **supersedes 메타데이터 선언**: 새 기술 문서가 구 문서를 완전히 대체할 때, 프론트매터에 `supersedes: "[[구문서]]"`를 못 박아 옛 지식의 영향력을 단절한다.
2. **지식의 증분 승격(Elevate)**: 프로젝트에서 얻은 일회성 트릭은 프로젝트 디렉토리에만 머물다 프로젝트와 함께 `900 Archive`로 보내고, 2개 이상의 독립된 프로젝트에서 반복 검증된 패턴만 `200 Dev KB`로 승격시킨다.
3. **무균실 유지**: 검증되지 않은 기술 스크랩은 절대 200번대에 들이지 않는다. 외부 자료는 무조건 `600 Content Observatory`에 격리해 두고, 내 손으로 직접 코드를 쳐보고 검증한 사실만 200번 백과사전으로 옮긴다.
