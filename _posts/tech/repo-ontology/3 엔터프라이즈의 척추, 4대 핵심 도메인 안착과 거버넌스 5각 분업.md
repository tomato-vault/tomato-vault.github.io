## 1. 엔터프라이즈 B2B SaaS의 무게: 수만 줄 코드와 복합 도메인의 도전

토이 프로젝트나 단순한 블로그 API에서는 온톨로지의 진가를 느끼기 어렵다. 테이블 대여섯 개, 엔드포인트 열댓 개 수준에서는 개발자의 머릿속만으로도 모든 맥락을 쥐고 흔들 수 있기 때문이다.

하지만 내가 프로덕션으로 운영하는 **대규모 학원 관리 B2B SaaS**는 완전히 다른 세상이다.

* **5대 사용자 계층(Actor)**: 슈퍼관리자, 학원장, 강사, 학부모, 학생
* **3개 플랫폼**: FastAPI 비동기 백엔드, React FSD 프론트엔드, Flutter 학부모 모바일 앱
* **복합 도메인**: 권한 인가, 실시간 키오스크 등하원, 일자별 출석부, 과제 제출 및 채점, 월별 수강료 청구와 결제/환불

이곳에서는 사소한 실수 하나가 치명적인 사고로 직결된다. 키오스크에서 등원 버튼이 두 번 눌려 학부모에게 중복 알림이 가거나, 타 학원의 수강료 원장이 노출되거나, 종강된 수업의 출석부가 수정되어 월별 통계가 어그러지는 일은 엔지니어링 실패이자 비즈니스 재앙이다.

사수도 동료도 없는 1인 개발 환경에서, 나는 매번 기억을 잃는 AI 에이전트들과 함께 이 거대한 시스템을 통제해야 했다. 그리고 그 해법은 바로 **핵심 도메인의 온톨로지화**였다.

## 2. 대규모 프로덕션 4대 도메인의 온톨로지 모델링 실전

우리는 가장 위험도가 높고 비즈니스 규칙이 빽빽한 **4대 핵심 도메인**을 우선적으로 온톨로지에 이식했다. (Objects 14개, Actions 6개, Rules 12개 구축 완료, `otlg lint` 0 violations).

```text
.ontology/
├── objects/
│   ├── user.yml, organization.yml, student-profile.yml
│   ├── class-model.yml, attendance.yml, check-in-out.yml
│   ├── assignment.yml, assignment-submission.yml, student-grades.yml
│   └── student-billing.yml, student-payment.yml, student-refund.yml
├── actions/
│   ├── authenticate-user.yml
│   ├── process-kiosk-check-in.yml, record-attendance.yml
│   ├── create-assignment.yml, grade-submission.yml
│   └── process-fee-payment.yml
└── rules/
    ├── auth-rules.yml
    └── fee-ledger-invariants.yml
```

### 1) 인증 및 멀티테넌시 도메인: 철통같은 데이터 격리

B2B SaaS의 생명은 테넌트 간 데이터 격리다. 아무리 뛰어난 기능도 타 학원의 정보가 1바이트라도 새어 나가면 끝장이다.

우리는 이를 시스템 전역 불변식인 `ORGANIZATION_DATA_ISOLATION` 규칙으로 못 박았다.

```yaml
# rules/auth-rules.yml
rule: ORGANIZATION_DATA_ISOLATION
name: "멀티테넌시 테넌트 데이터 격리 불변식"
scope: [Organization, User, Class, Attendance, Assignment, StudentBilling]
description: "모든 테넌트 종속 엔티티는 organization_id 외래키를 가지며, 모든 조회/수정/삭제 쿼리는 요청 주체의 primary_organization_id로 강제 필터링된다. 타 기관 데이터 접근은 403 Forbidden으로 차단된다."
enforcement:
  backend:
    dependency: "backend/app/api/deps.py:get_current_active_user"
    permission: "backend/app/core/permissions.py:require_organization_access"
```

에이전트가 어떤 도메인을 수정하든, `otlg trace`를 치면 이 규칙이 최상단에 빨간 불로 경고를 띄운다. 테넌트 검증을 빠뜨린 코드는 PR 게이트를 통과할 수 없다.

### 2) 출결 및 키오스크 도메인: 3중 방어선과 KST 기준

학원 입구의 키오스크 태블릿에서는 수백 명의 학생이 1~2초 간격으로 번호를 누르며 등원한다. 네트워크 랙으로 인한 따닥(Double Click) 클릭, 동시 요청 경합이 일상적으로 발생한다.

액션 `ProcessKioskCheckIn`은 이 동시성을 **3중 방어선(Three-tier Defense)**으로 완벽히 통제한다.

```yaml
# actions/process-kiosk-check-in.yml 발췌
preconditions:
  - id: "STUDENT_EXISTS_IN_ORG"
    rule: "check_in_out_crud.get_student_row(db, org_id, student_id) is not None"
    error: "해당 기관에 등록된 학생을 찾을 수 없습니다."
  - id: "NOT_ALREADY_CHECKED_IN"
    rule: "record.check_in_at is None"
    error: "이미 오늘 등원 처리가 완료된 학생입니다."
  - id: "CONCURRENCY_ROW_LOCK"
    rule: "SELECT ... FOR UPDATE 행 잠금 획득 및 (student_id, date) 유니크 인덱스로 중복 INSERT 차단"
    error: "동시 등원 처리 요청이 충돌했습니다."
```

또한 클라이언트의 시스템 시각은 언제든 조작되거나 틀어질 수 있으므로, 모든 출결 시각은 클라이언트 값을 무시하고 **서버 KST(Asia/Seoul, UTC+9)** 기준 시각으로만 기록하도록 강제했다.

### 3) 과제 및 성적 도메인: 원자적 채점과 통계 파이프라인

과제 채점(`GradeSubmission`)은 단순히 점수를 DB에 넣는 것으로 끝나지 않는다.

* 대상 과제물이 반드시 `SUBMITTED` 상태여야 한다는 사전조건 검증
* 해당 수업을 담당하는 강사 본인인지 확인하는 권한 인가
* 점수 부여 및 채점일시 갱신
* 해당 학생의 누적 성적 및 반별 통계(`assignment_stats_service`) 자동 재계산 이벤트 격발

이 모든 흐름이 `GradeSubmission.yml` 한 장에 일목요연하게 묶여 있다. 백엔드 서비스와 프론트엔드의 `AddTaskModal.js`까지 소스코드 바인딩이 걸려 있어, 에이전트는 프론트와 백엔드 간의 데이터 계약을 깨뜨리지 않고 작업할 수 있다.

### 4) 수강료 원장 도메인: 잔액 불변식과 회계 무결성

돈이 오가는 수강료 도메인은 한 치의 오차도 용납되지 않는다.

```yaml
# rules/fee-ledger-invariants.yml
rule: FEE_LEDGER_BALANCE_INVARIANT
name: "수강료 원장 잔액 및 결제 합치 불변식"
scope: [StudentBilling, StudentPayment, StudentRefund]
description: "청구 금액 = 기본 수강료 - 할인 총액 + 추가금. 결제 완료 후 잔액(remaining_amount)은 청구 금액 - 실결제 누적액 + 환불 누적액과 항상 일치해야 한다."
```

수강료 결제 액션인 `ProcessFeePayment`는 결제가 일어날 때마다 이 원장 잔액 공식을 검증하고, 결제 내역(`StudentPayment`)을 생성하며, 청구서(`StudentBilling`)의 상태를 `PAID` 또는 `PARTIALLY_PAID`로 원자적으로 전이시킨다.

## 3. 5각 거버넌스 분업 체계: 각자의 역할을 명확히 하라

온톨로지가 아무리 강력해도, 프로젝트의 모든 문서를 온톨로지에 욱여넣을 수는 없다. 아키텍처 다이어그램, 기술 스택 선정 이유, 에이전트 행동 수칙 등은 각자의 고유한 자리가 있어야 한다.

우리는 이 B2B SaaS 저장소에 **아키텍처 및 거버넌스 5각 분업 체계**를 확립했다.

```text
                      [ 프로덕션 엔지니어링 5각 분업 체계 ]

            1. 구조 (As-Is)                   2. 근거 (Why)
       docs/architecture/ (arc42)           docs/adr/ (ADR 5부)
                 ▲                                   ▲
                 │                                   │
                 └───────────────┬───────────────────┘
                                 │
                     3. 의미/불변식 (Invariants)
                       .ontology/ (repo-ontology)
                                 │
                 ┌───────────────┴───────────────────┐
                 │                                   │
                 ▼                                   ▼
          4. 규범 (Norms)                    5. 실행/테스트 (Reality)
       AGENTS.md (행동 강제)             backend/ frontend/ mobile/
```

| 역할 | 위치 | 정본 및 설명 |
| :--- | :--- | :--- |
| **1. 구조 (As-Is)** | `docs/architecture/` | **arc42 12절 + C4 Model**. 시스템의 현재 구조, 컴포넌트 경계, 외부 시스템 연동 계약 |
| **2. 근거 (Why)** | `docs/adr/` | **ADR (Michael Nygard 5-part)**. 아키텍처 결정의 역사적 배경, 대안 비교, 채택 이유 |
| **3. 불변식 (Invariants)** | `.ontology/` | **repo-ontology (`otlg`)**. 기계 판독 가능한 도메인 객체, 액션, 불변식 룰, 소스코드 바인딩 |
| **4. 규범 (Norms)** | `AGENTS.md` | **에이전트 행동 수칙**. 계층 의존성 강제, 금지 명령어, 타임존 등 행동 강제 규약 |
| **5. 실행 (Reality)** | `src/`, `tests/` | 실제 동작하는 프러덕션 소스코드와 자동화 테스트 스위트 |

어떤 문서도 다른 문서의 역할을 침범하지 않는다.
* 시스템의 전체 그림을 보고 싶다면 `arc42`를 본다.
* "이 기술을 왜 이렇게 결정했지?"가 궁금하다면 `ADR`을 본다.
* "이 비즈니스의 상태 변경 조건과 소스코드는 어디 있지?"를 알고 싶다면 `.ontology`를 추적한다.
* 에이전트의 손발을 묶는 가드레일은 `AGENTS.md`가 담당한다.
* 그리고 이 모든 것의 최종 진실은 테스트가 통과하는 코드로 증명된다.

이 5각 분업이 갖추어지자, 에이전트는 더 이상 무엇을 어디에 써야 할지 방황하지 않게 되었다.

## 4. 1인 개발자가 엔터프라이즈를 운영하는 궁극의 무기

혼자서 스타트업의 풀스택 제품을 만들고 운영한다는 것은, 매일 끝없는 엔트로피와의 전쟁을 치르는 것과 같다.

동료가 있다면 코드 리뷰를 통해 실수를 거르고, 아키텍처 회의를 통해 지식을 공유할 수 있다. 하지만 1인 개발자에게는 의논할 사수도, 내가 짠 코드의 결함을 짚어줄 시니어도 없다.

그 빈자리를 메우기 위해 도입했던 AI 에이전트는, 초기에는 엄청난 속도를 주는 듯했지만 이내 기억상실증과 환각으로 프로덕션에 시한폭탄을 심어놓곤 했다.

하지만 이제는 다르다.
1. **품질 엔진(TDD)**으로 테스트 주도의 안전망을 깔았고,
2. **병렬 하네스(cmux + Git Worktree)**로 작업 공간을 물리적으로 격리했으며,
3. **저장소 거버넌스(운영 대장 4종)**로 에이전트의 망각을 저장소의 기억으로 치환했고,
4. 마침내 **팔란티어식 실행 온톨로지(`repo-ontology`)**를 통해 비즈니스의 행동과 불변식을 코드에 1:1로 결합해냈다.

```text
[1인 개발자의 최종 엔지니어링 스택]
1. 규율: 계획 선행, TDD Red-Green, ODP 객체 분류
2. 격리: 1에이전트 1워크트리 병렬 하네스
3. 기록: WORKLOG, Watchlist, Tech-Debt, ADR
4. 실행: Objects, Links, Actions, Functions 실행 온톨로지
```

도구가 엄격해질수록, 개발자는 자유로워진다.

규칙을 머릿속에 담아두지 않고 시스템에 외주화했기에, 나는 비즈니스의 핵심 가치와 아키텍처 혁신에만 오롯이 집중할 수 있다. 1인이 엔터프라이즈급 프로덕션을 통제하는 비결은 초인적인 기억력이 아니라, **인간의 약점을 기계적으로 보완하는 단단한 운영체계**에 있었다.
