## 1. 왜 명사(DB 테이블)만으로는 부족한가

새로운 프로젝트에 투입되거나 대규모 레거시 코드를 인수받을 때, 우리는 가장 먼저 무엇을 찾는가? 열에 아홉은 **데이터베이스 ERD(Entity-Relationship Diagram)**다.

테이블 이름과 컬럼 목록, 외래키 화살표를 훑어보면 시스템의 윤곽이 잡히는 것처럼 느껴진다. "아, `users`가 있고, `classes`가 있고, `attendances`가 있구나."

하지만 코드를 짜기 시작하는 순간, ERD는 차가운 침묵에 빠진다.

```sql
-- ERD가 보여주는 것: 정적 스키마 (명사)
CREATE TABLE attendances (
    id BIGSERIAL PRIMARY KEY,
    class_id BIGINT NOT NULL REFERENCES classes(id),
    student_id BIGINT NOT NULL REFERENCES users(id),
    date DATE NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

실제 비즈니스 현장에서 일어나는 일은 이런 테이블 정의서 따위와는 비교할 수 없을 정도로 복잡하다.

1. **누가 실행할 수 있는가? (Actor & Permission)**
   * 아무나 출석을 바꿀 수 있는가? 학원 관리자(`ORGANIZATION_ADMIN`)나 해당 수업의 담당 강사(`TEACHER`)만 가능하다.
2. **어떤 조건에서만 실행 가능한가? (Preconditions & Invariants)**
   * 이미 종강한 수업의 출석을 바꿀 수 있는가? 안 된다. 수업 상태가 반드시 `IN_PROGRESS`여야 한다.
   * 다른 학원의 수업에 접근할 수 있는가? 절대 안 된다. 테넌트 격리(`organization_id`) 검증을 거쳐야 한다.
   * 동시에 두 명의 관리자가 같은 학생의 출석을 누르면 어떻게 되는가? 비관적 행 잠금(`FOR UPDATE`)으로 동시성 경합을 제어해야 한다.
3. **상태 변경 뒤에 무엇이 일어나는가? (Side Effects & Events)**
   * 출석 상태가 바뀌면 해당 월의 출석률 통계(`class_monthly_stats`)가 즉시 재계산되어야 한다.
   * 등원 체크인인 경우, 학부모 앱으로 비동기 푸시 알림이 발송되어야 한다.

이 방대한 비즈니스 진실은 어디에 적혀 있는가?
ERD에는 없다. 데이터베이스 제약조건에도 일부만 들어갈 뿐이다.

결국 이 모든 규칙은 **백엔드 서비스 레이어의 수많은 if문, 라우터의 Depends 함수, 프론트엔드 모달 팝업의 유효성 검사 코드** 속에 뿔뿔이 흩어져 봉인된다.

인간 개발자는 이 파편들을 몇 달에 걸쳐 야근하며 머릿속 뇌세포에 암기한다. 그리고 새 세션이 열릴 때마다 뇌가 포맷되는 AI 에이전트는, 이 파편화된 코드를 다 읽지 못해 사소한 불변식을 깨뜨리고 프로덕션 장애를 일으킨다.

코드베이스에 결핍되어 있던 것은 명사가 아니었다. 바로 **'동사(Action)'와 '불변식(Invariant)'**이었다.

## 2. 팔란티어의 4대 프리미티브: 코드베이스로의 이식

팔란티어 테크놀로지스(Palantir Technologies)는 이 문제를 수십 년 전부터 엔터프라이즈 환경에서 해결해 왔다. 파운드리(Foundry)와 AIP의 핵심 척추는 데이터 레이크가 아니라 바로 **온톨로지(Ontology)**다.

팔란티어가 정의한 온톨로지의 4대 핵심 구성 요소를 현대적인 모노레포/멀티플랫폼 소프트웨어 저장소에 맞게 재정의했다.

| 프리미티브 | 본질 | 소프트웨어 레포지토리에서의 정의 |
| :--- | :--- | :--- |
| **1. Objects (명사)** | 비즈니스 실체 | 도메인 엔티티. DB 테이블, 백엔드 ORM 모델, Pydantic 스키마, 프론트엔드 Entity 매핑 |
| **2. Links (관계)** | 객체 간의 결합 | 엔티티 간 연관 관계. 1:1, 1:N, N:M 외래키 관계 및 비즈니스적 상호작용 명시 |
| **3. Actions (동사)** | 원자적 상태 전이 | 비즈니스 트랜잭션. 실행 주체, 사전 불변식 검증, 상태 변이(Mutation), 부수 효과 정의 |
| **4. Functions (계산)** | 순수 도출 및 로직 | 상태 변경 없는 순수 함수(Pure Function). 통계 산출, AI 추론, 비즈니스 계산 공식 |

여기에 시스템 전체를 관통하는 전역 제약조건인 **Rules (불변식)**를 더해 4+1 체계를 완성했다.

```text
.ontology/
├── config.yml              # 프로젝트 메타데이터 및 스택 설정
├── objects/                # Objects: User, Class, Attendance, Assignment
├── links/                  # Links: Class -> Attendance, User -> Profile
├── actions/                # Actions: RecordAttendance, GradeSubmission
├── functions/              # Functions: CalculateAttendanceRate
└── rules/                  # Rules: ORGANIZATION_DATA_ISOLATION
```

## 3. 기계 가독형 YAML 스키마 설계

온톨로지는 사람이 읽는 위키 문서가 아니다. AI 에이전트와 CLI 도구, 그리고 CI 파이프라인이 오차 없이 파싱하고 검증할 수 있는 **엄격한 기계 가독형 명세**여야 한다.

우리는 JSON Schema 대신 가독성과 주석을 온전히 보존할 수 있는 YAML 규격을 택했고, 파이썬의 Pydantic v2를 통해 로딩 시점에 엄격한 유효성 검증을 거치도록 설계했다.

### 1) Action 명세: 상태 전이의 완벽한 캡슐화

실제 프로덕션 학원 관리 B2B SaaS 시스템에서 학생들의 출석을 기록하는 액션인 `RecordAttendance.yml`의 실제 스펙이다.

```yaml
action: RecordAttendance
domain: "class-attendance"
tags: ["attendance", "class", "upsert", "stats"]
description: "강사 또는 학원 관리자가 특정 수업(Class)에서 학생들의 일자별 출석 상태를 일괄 기록하거나 수정(Upsert)한다. 저장 즉시 영향받은 월의 출석률 통계가 재계산된다."

# 1. 실행 주체와 권한 계약
actor:
  type: User
  roles: ["ORGANIZATION_ADMIN", "TEACHER"]
  permission: "classes:attendance:write"

# 2. 작업 대상 엔티티
target:
  object: Class
  lookup: "id"

# 3. 입력 파라미터 스펙
parameters:
  class_id:
    type: integer
    required: true
    description: "출석을 기록할 대상 수업 ID"
  records:
    type: array
    required: true
    min_items: 1
    items:
      student_id:
        type: integer
        required: true
      date:
        type: date
        required: true
      status:
        type: enum
        values: ["PRESENT", "LATE", "EARLY_LEAVE", "ABSENT", "EXCLUDED"]
        required: true

# 4. 사전 불변식 (Preconditions)
preconditions:
  - id: "CLASS_EXISTS_AND_SAME_ORG"
    rule: "db_class is not None and db_class.organization_id == actor.primary_organization_id"
    error: "수업을 찾을 수 없습니다. (ID: {class_id})"
  - id: "CLASS_IN_PROGRESS_ONLY"
    rule: "db_class.status == ClassStatus.IN_PROGRESS"
    error: "강의 중인 수업에서만 출석을 기록할 수 있습니다. (현재: {status_name})"
  - id: "VALID_ATTENDANCE_STATUS"
    rule: "record.status in ['PRESENT', 'LATE', 'EARLY_LEAVE', 'ABSENT', 'EXCLUDED']"
    error: "출석 상태는 PRESENT, LATE, EARLY_LEAVE, ABSENT, EXCLUDED 중 하나여야 합니다."

# 5. 상태 변경과 부수 효과 (Effects)
effects:
  mutate:
    attendances: "기존 JSONB 데이터를 불러와 학생을 이전 상태에서 제거하고 새 상태 배열에 추가한 후 (class_id, date) 단위로 Upsert"
    class_monthly_stats: "변경된 날짜들의 연월(YYYY-MM)을 집계하여 해당 월의 출석률 통계를 자동 재계산"
  events:
    - name: "ATTENDANCE_UPDATED"
      channel: "internal_stats_pipeline"
      trigger: "attendance_stats_service.update_stats_on_attendance_change"

# 6. 소스코드 1:1 바인딩 (Code Binding)
code_binding:
  backend:
    service: "backend/app/services/attendance_service.py:AttendanceService.save_attendance"
    stats_service: "backend/app/services/attendance_stats_service.py:AttendanceStatsService.update_stats_on_attendance_change"
    api: "POST /api/v1/classes/{class_id}/attendance"
    request_schema: "backend/app/schemas/attendance.py:AttendanceSaveRequest"
  frontend:
    feature: "frontend/src/features/attendance"
    api: "frontend/src/features/attendance/api/attendance.api.js:saveAttendance"
    model: "frontend/src/features/attendance/model/attendance.service.js"
```

이 명세 하나만 읽으면 시스템의 모든 것이 드러난다.
* 누가 호출할 수 있는가?
* 어떤 조건을 만족해야 코드가 터지지 않는가?
* 데이터베이스의 어느 테이블이 바뀌고, 어떤 비동기 이벤트가 격발되는가?
* 백엔드의 어떤 함수, 프론트엔드의 어떤 파일이 여기에 관여하는가?

## 4. 소스코드 1:1 바인딩: 문서와 코드의 일체화

기존의 아키텍처 문서가 실패했던 가장 큰 이유는 **문서와 코드가 서로 다른 차원에 존재했기 때문**이다. 문서는 노션이나 Confluence에 있었고, 코드는 깃허브에 있었다. 코드가 바뀌어도 문서는 갱신되지 않았고, 결국 문서는 썩어갔다(Drift).

`repo-ontology`는 이 문제를 **코드 바인딩(Code Binding)**으로 해결했다.

```text
                  [ Action: RecordAttendance ]
                               │
       ┌───────────────────────┼───────────────────────┐
       ▼                       ▼                       ▼
  [ Backend ]            [ Frontend ]              [ Mobile ]
FastAPI Service        FSD Feature Slice        Flutter ViewModel
- attendance_service   - features/attendance    - check_in_out_vm
- attendance_api       - attendance.api.js      - check_in_out_repo
- attendance_schema    - attendance.service.js  - check_in_out.dart
```

온톨로지는 허공에 뜬 추상적인 개념이 아니다. 파일 경로와 클래스명, 함수명을 정확하게 가리키는 **절대 좌표계**다.

만약 개발자가 리팩토링 과정에서 `backend/app/services/attendance_service.py`의 파일명을 바꾸거나 `save_attendance` 메서드를 삭제하면 어떻게 될까?

CLI 검증 도구인 `otlg lint`가 정적 분석을 통해 즉시 경고를 띄운다:

```bash
$ otlg lint
[ERROR] Action 'RecordAttendance': backend service path not found: backend/app/services/attendance_service.py
1 violations found.
```

코드가 바뀌면 온톨로지 바인딩이 깨지고, 온톨로지가 깨지면 CI가 실패한다. 문서와 코드가 비로소 하나의 생명주기로 묶인 것이다.

## 5. 지식 온톨로지와 실행 온톨로지의 결정적 차이

앞선 0편에서도 언급했듯, 이 체계는 옵시디언 볼트에서 구축했던 개인 지식 온톨로지와는 차원이 다르다. 두 온톨로지의 차이를 정리하면 다음과 같다.

| 비교 항목 | 개인 지식 온톨로지 (Vault OS) | 코드 실행 온톨로지 (Repo Ontology) |
| :--- | :--- | :--- |
| **관리 대상** | 4,000개의 마크다운 생각 노트 | 수만 줄의 프로덕션 소스코드 |
| **중심 축** | **명사 (Noun)**: 분류, 계보, 선행 지식 | **동사 (Verb)**: 행동, 상태 전이, 불변식 |
| **관계 표현** | `builds_on` (이 문서를 읽기 전 필요한 지식) | `preconditions`, `effects`, `events` |
| **바인딩** | 마크다운 링크 (`[[문서명]]`) | 파일 시스템 AST 좌표 (`file.py:Class.method`) |
| **실행 주체** | 생각하는 인간 연구자 | 기억상실증을 앓는 AI 코딩 에이전트 |
| **실패의 결과** | 지식 탐색의 지연 및 산만함 | 프로덕션 데이터 오염 및 서비스 장애 |

Vault의 온톨로지가 '생각의 도서관'을 짓는 작업이었다면, Repo Ontology는 '원자력 발전소의 제어판'을 설계하는 작업이다. 버튼 하나를 누를 때 어떤 밸브가 열리고 어떤 경보가 울리는지가 한 치의 오차도 없이 명세화되어 있어야 한다.
