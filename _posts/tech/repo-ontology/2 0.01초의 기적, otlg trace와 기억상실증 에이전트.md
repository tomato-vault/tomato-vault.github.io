## 1. 기억상실증 에이전트의 현실과 무차별 탐색의 한계

AI 에이전트와 페어 프로그래밍을 해본 사람이라면 누구나 겪는 깊은 피로감이 있다. 바로 **에이전트의 기억상실증(Amnesia)**이다.

터미널 창을 닫고 새로운 작업 세션이 시작되면, 에이전트는 어제 자신이 짰던 코드도, 이 시스템이 어떤 비즈니스 원칙으로 굴러가는지도 전혀 알지 못하는 순수한 백지상태(Tabula Rasa)로 돌아간다.

이 상태에서 "출석 체크인 기능을 수정해줘"라고 요청하면 어떤 일이 벌어질까?

```text
[에이전트의 무차별 탐색(Brute-force) 과정]
1. find_by_name: *attendance*, *check_in* (수십 개 파일 검색)
2. grep_search: "def check_in" (관련 없는 레거시 코드까지 히트)
3. view_file: backend/app/api/... (파일을 수백 줄씩 읽으며 토큰 소모)
4. view_file: frontend/src/... (엉뚱한 UI 컴포넌트 탐색)
5. 결과: 컨텍스트 윈도우 절반이 쓸데없는 코드로 가득 차고, 핵심 불변식은 놓침
```

수만 줄에 달하는 프로덕션 코드베이스에서 에이전트가 코드를 뒤적거리며 탐색하는 동안, 엄청난 양의 API 토큰이 낭비되고 시간은 수 분씩 지연된다.

더 심각한 문제는 **'환각과 불변식 누락'**이다. 출석 체크인 로직 뒤에 숨겨진 동시성 행 잠금(`FOR UPDATE`)이나 테넌트 격리 검증을 에이전트가 탐색 과정에서 놓치면, 겉보기엔 그럴싸하지만 동시 요청 시 중복 출석이 찍히거나 타 기관의 학생 정보가 노출되는 치명적인 보안 결함 코드를 뱉어내게 된다.

에이전트에게 필요한 것은 '더 많은 코드를 읽을 수 있는 거대한 컨텍스트 창'이 아니었다. **'어떤 작업을 할 때 무엇을 지켜야 하고 어디를 고쳐야 하는지 0.01초 만에 짚어주는 정확한 내비게이터'**였다.

## 2. `otlg trace`: 0.01초 만에 도메인 풀체인을 인출하다

우리는 이 문제를 해결하기 위해 온톨로지 전용 CLI인 `otlg`에 **`trace` 명령**을 구축했다.

이제 에이전트가 새로운 세션에서 작업을 시작할 때 코드를 찾아 헤맬 필요가 없다. 터미널에서 단 한 줄의 명령만 실행하면 된다.

```bash
$ otlg trace attendance
```

이 명령을 치는 순간, `otlg` 엔진은 메모리에 적재된 온톨로지 레지스트리를 고속 그래프 순회하여 다음과 같은 결과를 즉시 터미널에 쏟아낸다.

```text
╭─────────────────── Ontology Trace: attendance ───────────────────╮
│ Matched Domains: class-attendance                                │
│                                                                  │
│ ## 📦 Affected Objects                                           │
│ - Attendance (class-attendance): 학생의 수업별 일자별 출석 기록  │
│   - Properties: id, class_id, student_id, date, status, notes... │
│ - CheckInOut (student-management): 키오스크 등하원 출입 기록     │
│ - Class (class-management): 학원 개설 강좌 및 수업 단위          │
│                                                                  │
│ ## ⚡ Affected Actions                                           │
│ - ProcessKioskCheckIn → CheckInOut: 키오스크에서 등하원 확정     │
│   - Precondition: `record.check_in_at is None`                   │
│   - Precondition: `SELECT ... FOR UPDATE 행 잠금 획득`           │
│ - RecordAttendance → Class: 강사/관리자의 일자별 출석 일괄 저장  │
│   - Precondition: `db_class.organization_id == actor.org_id`     │
│   - Precondition: `db_class.status == ClassStatus.IN_PROGRESS`   │
│   - Precondition: `record.status in ['PRESENT', 'LATE', ...]`    │
│                                                                  │
│ ## 🛡️ Relevant Rules & Invariants                                │
│ - `ORGANIZATION_DATA_ISOLATION` (테넌트 데이터 격리 불변식):     │
│   모든 조회/수정은 primary_organization_id로 강제 필터링된다.    │
│   - Enforcement (backend): permissions.py:require_org_access     │
│                                                                  │
│ ## 📂 Source Code Paths                                          │
│ - backend/app/api/my/attendance.py                               │
│ - backend/app/crud/attendance_crud.py                            │
│ - backend/app/models/attendance.py                               │
│ - backend/app/schemas/attendance.py                              │
│ - backend/app/services/attendance_service.py                     │
│ - backend/app/services/attendance_stats_service.py               │
│ - frontend/src/features/attendance/api/attendance.api.js         │
│ - frontend/src/features/attendance/model/attendance.service.js   │
│ - mobile/lib/data/models/check_in_out.dart                       │
╰──────────────────────────────────────────────────────────────────╯
```

소요 시간은 단 **0.01초**다.

에이전트는 grep을 한 번도 돌리지 않고도:
1. 이 작업에 관여하는 핵심 객체가 무엇인지
2. 호출 가능한 액션과 그 액션이 요구하는 엄격한 사전 불변식(행 잠금, 상태 검증)이 무엇인지
3. 반드시 지켜야 할 전역 아키텍처 규칙이 무엇인지
4. 백엔드, 프론트엔드, 모바일에서 수정해야 할 **정확한 소스코드 파일 경로 수십 개**를 완벽하게 파악한다.

기억을 잃은 에이전트는 0.01초 만에 프로덕션 엔지니어의 도메인 지식을 완전히 장착하게 된다.

## 3. 정적 무결성 검증: `otlg lint`와 코드 드리프트 방지

온톨로지가 아무리 우아해도, 실제 소스코드와 어긋나기 시작하면(Drift) 없는 것만 못하다. 온톨로지에 적힌 파일 경로가 옛날 경로이거나, 클래스 메서드가 삭제되었는데 온톨로지에는 남아 있다면 에이전트는 더 큰 혼란에 빠진다.

그래서 `repo-ontology`는 온톨로지와 소스코드 간의 완벽한 동기화를 보장하는 정적 린터인 **`otlg lint`**를 기본 내장하고 있다.

```bash
$ otlg lint
```

`otlg lint`는 다음 4가지 핵심 무결성을 전수 검사한다:

1. **코드 파일 실재성 검증**:
   * YAML 명세의 `code_binding`에 적힌 백엔드/프론트엔드/모바일 파일이 실제 프로젝트 디렉토리에 존재하는가?
2. **심볼(Symbol) AST 검증**:
   * 지정된 파일 안에 해당 클래스나 메서드(`AttendanceService.save_attendance`)가 실제로 존재하는가?
3. **참조 정합성 검증**:
   * Action의 Target 객체가 `objects/`에 실제로 선언되어 있는가?
   * Link의 Source와 Target 객체가 실재하는가?
4. **전역 규칙 스코프 검증**:
   * Rule의 `scope`에 적힌 엔티티들이 유효한 온톨로지 객체인가?

```text
[검증 실패 예시]
$ otlg lint
[ERROR] Action 'RecordAttendance': Bound code file does not exist: 'backend/app/services/old_attendance.py'
[ERROR] Action 'RecordAttendance': Symbol 'save_attendance_v2' not found in 'backend/app/services/attendance_service.py'
2 violations found.
```

개발자가 리팩토링 과정에서 서비스 메서드 이름을 바꾸고 온톨로지를 갱신하지 않으면, CI 파이프라인에서 `otlg lint`가 즉시 빌드를 중단시킨다. 온톨로지는 문서가 아니라 **테스트 가능한 코드**로서 관리된다.

## 4. TDD 스캐폴딩: 불변식이 곧 테스트 케이스가 된다

온톨로지의 가치는 탐색에만 머무르지 않는다. 바로 앞선 시리즈에서 다루었던 **품질 엔진(TDD)**과 직결된다.

TDD를 할 때 가장 많은 뇌 에너지를 소모하는 구간은 "어떤 테스트 케이스를 작성해야 하는가?"이다. 정상 동작(Happy Path)은 누구나 쉽게 떠올리지만, 실패해야 마땅한 경계 조건(Edge Cases)은 자주 빠뜨린다.

온톨로지의 Action에 정의된 **`preconditions`**는 그 자체로 완벽한 **TDD 명세서**가 된다.

```yaml
# RecordAttendance의 preconditions
preconditions:
  - id: "CLASS_EXISTS_AND_SAME_ORG"
    rule: "db_class is not None and db_class.organization_id == actor.primary_organization_id"
    error: "수업을 찾을 수 없습니다."
  - id: "CLASS_IN_PROGRESS_ONLY"
    rule: "db_class.status == ClassStatus.IN_PROGRESS"
    error: "강의 중인 수업에서만 출석을 기록할 수 있습니다."
  - id: "VALID_ATTENDANCE_STATUS"
    rule: "record.status in ['PRESENT', 'LATE', 'EARLY_LEAVE', 'ABSENT', 'EXCLUDED']"
    error: "출석 상태가 유효하지 않습니다."
```

이 세 줄의 선언은 백엔드 pytest 테스트 스위트의 세 가지 필수 테스트 함수로 1:1 직결된다:

```python
# 온톨로지 사전조건에서 도출된 필수 실패 테스트 스위트
def test_record_attendance_fails_when_other_org_class():
    """CLASS_EXISTS_AND_SAME_ORG: 타 학원 수업 출석 시도 시 404/403 차단 검증"""
    ...

def test_record_attendance_fails_when_class_ended():
    """CLASS_IN_PROGRESS_ONLY: 종강된 수업 출석 변경 시 400 Bad Request 차단 검증"""
    ...

def test_record_attendance_fails_on_invalid_status():
    """VALID_ATTENDANCE_STATUS: 허용되지 않은 출석 코드 입력 시 유효성 검증 실패"""
    ...
```

인간 개발자나 에이전트가 머리를 쥐어짜며 예외 케이스를 상상할 필요가 없다. 온톨로지의 사전조건을 하나씩 테스트 코드로 변환하여 Red를 띄우고, 비즈니스 로직을 통과시켜 Green을 만들면 기능 구현이 끝난다.

온톨로지가 TDD의 요구사항 명세서 역할을 완벽하게 대체하는 것이다.

## 5. 에이전트에게 뇌를 주지 말고 척추를 주어라

많은 이들이 AI 코딩 에이전트의 실수를 줄이기 위해 시스템 프롬프트에 구구절절 수십 줄의 당부사항을 적는다.

> "너는 시니어 엔지니어로서 멀티테넌시 보안을 최우선으로 해야 해. 다른 학원의 데이터를 넘나들지 않도록 주의하고, 동시성 이슈를 고려해서 락을 걸어야 해..."

단언컨대, 이런 자연어 잔소리는 반드시 샌다. 에이전트의 주의력(Attention)은 한정되어 있고, 코드가 길어지면 자연어 규칙은 가장 먼저 망각된다.

에이전트에게 필요한 것은 추상적인 도덕률이 아니라, **결정론적인 기계적 척추(Deterministic Mechanical Backbone)**다.

* **무엇을 모르는가?** ➔ `otlg trace`로 0.01초 만에 필요한 맥락만 주입한다.
* **코드가 빗나갔는가?** ➔ `otlg lint`로 기계적으로 튕겨낸다.
* **어떻게 검증하는가?** ➔ `preconditions`를 기반으로 TDD 실패 테스트를 강제한다.

규칙을 말로 설명하지 않고 도구로 강제할 때, 기억상실증 에이전트는 가장 신뢰할 수 있는 일류 동료로 거듭난다.
