## 1. 자만: "나는 이미 온톨로지를 정복했다"

불과 며칠 전까지만 해도, 나는 내가 온톨로지(Ontology)의 본질을 완벽하게 이해하고 통제하고 있다고 믿었다.

개인 지식베이스인 옵시디언 볼트에 RDF와 온톨로지 개념을 도입하여, 4,000개가 넘는 문서에 13개의 엄격한 `type`을 부여하고, 380건의 `builds_on` 관계로 지식의 선행 계보도를 짰다. 에이전트가 함부로 태그를 달지 못하도록 250개 화이트리스트를 구축했고, `vault new` CLI를 만들어 스키마를 통과하지 못한 파일은 아예 생성조차 되지 않도록 차단했다.

그래프 뷰를 열면 모든 개념이 질서정연하게 서로를 딛고 서 있었고, `vault lint`는 단 1건의 위반도 없이 깨끗한 정상 상태를 띄웠다.

*"이 정도면 온톨로지를 소프트웨어 공학적으로 가장 우아하게 다룬 것 아닌가?"*

솔직히 뿌듯했다. 인간의 직관과 AI 에이전트의 환각 사이에서 이토록 단단한 규칙의 성벽을 쌓아 올린 사례는 흔치 않다고 자부했다. 하지만 그 자만심은 오래가지 않았다. 2026 스타트업 페스티벌 'Try Everything'의 한 세션을 보기 전까지는 말이다.

## 2. 충격: 팔란티어 키노트가 던진 일갈

화면 속에는 세계적인 데이터 운영체제 기업 팔란티어(Palantir Foundry / AIP)의 두 엔지니어, Alex와 Rosa가 서 있었다. 슬라이드 쇼 대신 당일 아침에 바로 빌드업한 실제 라이브 프로덕션 환경을 띄워놓고 소프트웨어를 시연하던 그들은, 내 머리를 둔기로 후려치는 듯한 문장을 던졌다.

> *"We hate dashboards. 이미 알고 있는 데이터를 예쁘게 모아서 보여주는 대시보드는 우리에게 무의미합니다(meaningless). 중요한 것은 데이터가 아니라, 비즈니스 실체를 대변하는 객체(Objects)와, 현장의 실무자가 즉각 조치를 취할 수 있는 **행동(Actions)**, 그리고 이를 통제하는 **불변식(Invariants)**입니다."*

그 순간, 온몸에 소름이 돋았다.

내가 볼트에서 만들어 놓은 온톨로지는 냉정하게 말해 **"예쁜 대시보드이자 잘 정돈된 도서관 분류표"**에 불과했던 것이다.

* "이 문서는 concept인가, procedure인가?" (명사적 분류)
* "이 개념을 이해하려면 어떤 상위 문서를 읽어야 하는가?" (정적 관계)

이것은 지식의 부패를 막는 데는 훌륭한 정적 지식망(Knowledge Taxonomy)이었지만, **실제 세상의 문제를 풀고 소프트웨어의 상태를 변경하는 실행형 온톨로지(Actionable Ontology)의 세계와는 아득히 먼 거리가 있었다.**

팔란티어가 말하는 온톨로지는 단순한 지식 그래프가 아니었다. 수만 개의 레거시 데이터셋 위에서 비즈니스 객체(Plant, Order, Shipment)를 띄워 올리고, 그 객체 위에서 권한과 사전 조건을 검증하여 **상태를 안전하게 변경하는 원자적 트랜잭션(Action)**을 실행하는 **기업의 디지털 트윈이자 모든 실행의 척추(Backbone)**였다.

## 3. 결핍: 코드베이스에는 왜 '동사(Action)'가 없는가

키노트를 보고 난 뒤, 내가 관리하던 가장 거대한 프로덕션 저장소인 B2B 학원 관리 SaaS의 코드를 열어보았다. 그리고 그동안 에이전트들과 일하며 겪었던 수많은 마찰과 피로의 근본 원인이 무엇이었는지 단번에 깨달았다.

### 1) ERD는 '명사'만 보여준다

우리는 흔히 DB 스키마와 ERD를 보면 시스템을 다 안다고 착각한다. 하지만 ERD는 테이블의 형태(명사)만 보여줄 뿐이다.

* "강사가 학생의 과제를 채점한다(GradeSubmission)"는 행위는 단순한 `UPDATE submissions SET score = 90`이 아니다.
* "과제는 반드시 제출 완료(SUBMITTED) 상태여야 한다"는 도메인 불변식이 있어야 하고,
* "해당 수업을 담당하는 강사 본인만 채점할 수 있다"는 권한 불변식이 있어야 하며,
* 점수 부여, 채점일시 기록, 그리고 학생에게 백그라운드 푸시 알림을 쏘는 부수 효과(Side Effects)가 원자적으로 묶여야 한다.

이러한 **동사(Action)와 불변식(Invariants)**은 어디에 있는가?
수만 줄의 백엔드 서비스 코드, 라우터의 Depends 함수, 프론트엔드의 모달 컴포넌트 구석구석에 파편화되어 흩어져 있었다.

### 2) 기억상실증 에이전트의 비극

터미널을 닫고 새 세션이 열린 AI 에이전트는 이 흩어진 규칙을 알지 못한다.

"출석 체크인 기능을 수정해줘"라고 요청하면, 에이전트는 출석의 비즈니스 불변식을 알기 위해 수십 개의 백엔드 서비스와 프론트엔드 파일을 끝없이 뒤지고 grep을 돌린다. 그러다 3중 방어 행 잠금(`FOR UPDATE`)이나 테넌트 격리 로직을 놓치고 엉뚱한 코드를 짜기 일쑤였다.

기존 6편에서 정립했던 운영 대장 4종(`WORKLOG`, `Watchlist`, `Tech-Debt`, `ADR`)은 훌륭한 거버넌스였지만, 여전히 사람이 수기로 명세를 관리해야 하는 한계(Drift)가 있었다.

> *"에이전트에게 소스코드를 다 읽히지 않고, 도메인의 객체와 액션, 그리고 소스코드 1:1 바인딩을 기계가 읽을 수 있는 온톨로지로 제공할 수는 없을까?"*

## 4. 해법: `repo-ontology (otlg)`의 탄생

망설일 이유가 없었다. 팔란티어의 온톨로지 프리미티브를 코드 레포지토리에 이식하는 전용 템플릿과 CLI 도구 개발에 즉시 착수했다.

그렇게 탄생한 것이 바로 **`repo-ontology` (전역 CLI: `otlg`)**다.

```text
<project-root>/
├── .ontology/
│   ├── config.yml              # 프로젝트 메타데이터 및 스택 설정
│   ├── objects/                # 도메인 엔티티 (User, Class, Attendance)
│   ├── links/                  # 엔티티 간 관계도 (1:1, 1:N, N:M)
│   ├── actions/                # 상태 전이 트랜잭션 (GradeSubmission, RecordAttendance)
│   ├── functions/              # 순수 계산 및 도출 함수 (CalculateAttendanceRate)
│   └── rules/                  # 전역 비즈니스 불변식 (ORGANIZATION_DATA_ISOLATION)
├── docs/architecture/          # 구조 (arc42 12절 + C4 Model)
├── docs/adr/                   # 근거 (Michael Nygard 5-part ADR)
├── AGENTS.md                   # 규범 (AI 에이전트 공통 행동 규율)
└── backend/ frontend/ mobile/  # 실행 (실제 소스코드)
```

우리는 시스템을 4대 핵심 프리미티브로 기계 가독형 정의했다:

1. **Objects (명사)**: 도메인 엔티티와 실제 소스코드 Model/Schema 1:1 바인딩
2. **Links (관계)**: 엔티티 간의 외래키 및 비즈니스 연관 관계
3. **Actions (동사)**: 원자적 상태 변경 트랜잭션, 실행 전 불변식(`preconditions`), 부수효과, 서비스 코드 바인딩
4. **Functions (계산)**: 상태 변경 없는 순수 계산 로직 및 통계 산출 함수

그리고 이 온톨로지를 B2B SaaS의 4대 핵심 도메인(인증, 출석, 과제/성적, 수강료 수납)에 전격 이식했다. (Objects 14개, Actions 6개, Rules 12개 구축 완료, `otlg lint` 0 violations).

결과는 놀라웠다. 새로 띄운 에이전트에게 터미널에서 다음 명령을 내리면:

```bash
$ otlg trace attendance
```

단 **0.01초** 만에 출석 도메인의 모든 관여 객체, 허용된 액션, 사전 불변식(3중 방어 행 잠금, 테넌트 검증), 그리고 건드려야 할 백엔드/프론트엔드/모바일의 **정확한 소스 파일 경로 수십 개가 완벽하게 정렬되어 인출**된다.

에이전트는 더 이상 코드를 헤매지 않는다. 온톨로지가 제공하는 도메인 불변식이라는 가드레일 위에서, 가장 안전하고 완벽한 코드를 즉시 작성하기 시작했다.

### 엔터프라이즈의 스케일과 1인 개발자의 현실적 경량화

솔직히 말해, 팔란티어가 다루는 글로벌 엔터프라이즈의 스케일과 1인 개발자인 내가 마주한 스케일 사이에는 분명한 체급 차이가 존재한다. 수만 명의 다국적 기업이 쓰는 전사 데이터 레이크(Data Lake)의 모든 공급망을 온톨로지화하는 것과, 단일 B2B SaaS의 4대 핵심 도메인을 온톨로지화하는 것은 물리적인 크기가 다르다.

하지만 **"시스템의 복잡도를 기계가 검증 가능한 객체(Objects)와 행동(Actions), 그리고 불변식(Invariants)으로 통제한다"는 아키텍처의 본질은 스케일과 무관하게 동일하다.**

나는 수천억짜리 거대 엔터프라이즈 플랫폼의 외형을 맹목적으로 모방하려 하지 않았다. 대신 1인 개발자가 매번 기억을 잃는 AI 에이전트와 협업할 때 겪는 가장 고통스러운 병목, 즉 '도메인 불변식의 망각과 코드 탐색 비용'을 해결하는 데 모든 초점을 맞췄다. 거대 플랫폼의 4대 프리미티브에서 불필요한 무게를 덜어내고, 단일 코드 저장소에 맞게 가장 실용적이고 날카로운 툴체인(`repo-ontology`)으로 압축해 낸 이유다.

비록 시작은 학원 관리 SaaS의 4대 핵심 도메인이었지만, 이 프레임워크는 어떤 도메인이나 더 거대한 엔터프라이즈 환경을 마주하더라도 즉각 흔들림 없는 온톨로지 운영체계를 세울 수 있는 단단한 기초 체력이 되어주었다.
