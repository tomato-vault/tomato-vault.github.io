## 개요

지난 [[2편] 4,400개의 흩어진 생각에 척추를 세우다](/tag-ontology-engineering/2-vault-knowledge-ontology/) 말미에서 살짝 언급했다시피, `Obsidian Vault`에 적용한 온톨로지 개념을 코드 레포지토리에 그대로 이식하면 에이전트와의 협업을 굉장히 효율적으로 운용할 수 있지 않을까라는 고민을 하게 되었다. 이번 글에서는 `Vault`에 적용한 지식 온톨로지의 한계를 자각하고, 그 개념을 실제 코드 `Repository`로 이식해 내기까지의 중간 사유 과정을 설명한다.

---

## 자만: "나는 이미 온톨로지를 정복했다"

온톨로지라는 것이 애초에 좀 많이 헷갈리는 개념이다 보니, 나는 지난 글에서 이야기한 것 수준의 체계를 온톨로지의 전부라고 인지하고 있었다. 4,400여 개의 문서에 13개의 엄격한 `type`을 부여하고, `builds_on`과 7가지 의미 관계로 지식의 계보를 엮어낸 뒤, `vault new` 생성 게이트와 `vault lint` 무결성 검증까지 통과시켰을 때만 해도 내심 큰 성취감에 취해 있었다. 화면 가득 질서정연하게 얽힌 그래프 뷰를 바라보며, 나는 내가 온톨로지라는 추상적인 개념을 소프트웨어 공학적으로 꽤나 우아하게 정복했다고 착각하고 있었던 것이다.

그런데 문득 생각해보니 한 가지 기묘한 의문이 들었다. **'아니, 이 정도 수준인데 왜 세상 사람들은 `Palantir`와 온톨로지에 대해 그렇게 호들갑이지?'**라는 의문이었다. 아무리 내 볼트 검색이 0.5ms 만에 끝나고 문서 분류가 깔끔해졌다 한들, 그것만으로 수조 원짜리 엔터프라이즈 시장의 패러다임을 바꾼다고 말하기에는 무언가 결정적인 고리가 빠져 있는 느낌이었다. 그래서 조금 더 자료를 찾아보고 AI에게 집요하게 질의하며 파고들어 봤더니, 내가 만든 것은 넓은 의미의 지식 분류 온톨로지에는 들어갈 수 있을지언정 `Palantir`가 구축해 놓은 운영 온톨로지(`Operational Ontology`)와는 격이 다르다는 사실을 알게 되었다.

## 충격: 팔란티어 키노트가 던진 일갈 ("We hate dashboards")

그 격차를 가장 선명하게 일깨워 준 계기가 바로 2026 스타트업 페스티벌 'Try Everything'에서 진행되었던 `Palantir` 엔지니어 Alex와 Rosa의 키노트 세션이었다. 발표 무대에 오른 두 엔지니어는 흔한 장표 하나 띄우지 않고 *"We hate slides. We truly hate slides."*라고 선언하더니, 그날 아침에 바로 빌드업한 라이브 프로덕션 환경을 화면에 띄워 실제 기업의 공급망 데이터를 실시간으로 조작해 보였다.

수만 개의 레거시 데이터셋(`Oracle`, `SAP`, `Snowflake`)이 온톨로지 객체(`Plant`, `Shipment`, `Order`)로 정제되어 모든 워크플로우의 불변의 척추(Ultimate Backbone)로 작동하는 모습도 인상적이었지만, 내 머리를 망치로 맞은 듯 울렸던 대목은 그들이 대시보드를 정의하는 방식이었다.

> *"이미 알고 있는 데이터를 예쁘게 모아서 보여주는 대시보드는 우리에게 무의미합니다(meaningless). 진정한 가치는 데이터를 보고 즉각적인 신호를 보내며, 그 자리에서 **실제 행동(Action)**을 취해 시스템의 상태를 바꾸는 데 있습니다."*

그 한마디에 내가 애지중지 쌓아 올렸던 볼트 온톨로지의 민낯이 그대로 드러났다. 돌아보면 내가 `Obsidian Vault`에 세운 온톨로지는 냉정하게 말해 **'예쁘게 정돈된 대시보드이자 훌륭한 도서관 분류표(Taxonomy)'**에 머물러 있었다. "이 문서는 `concept`인가 `procedure`인가?", "이 문서를 이해하려면 무엇을 먼저 읽어야 하는가?"라는 질문은 정적인 지식이 썩지 않게 보관하는 데는 더할 나위 없이 훌륭했지만, 정작 살아 움직이는 프로덕션 코드베이스에서 무엇을 바꾸고 어떤 제약을 강제할 것인가를 다루는 **실행형 온톨로지(Actionable Ontology)**와는 거리가 멀었던 것이다.

## 본질: 지식은 명사지만 코드는 동사다

도서관 사서의 시각에서 벗어나 실제 소프트웨어가 돌아가는 엔지니어링 현장의 시각으로 온톨로지를 다시 바라보자, 지난 2편 말미에서 나를 괴롭혔던 질문("왜 문서 온톨로지가 완벽한데도 실제 코드는 여전히 터지는가?")의 원인이 비로소 명확해졌다. 내가 다루는 두 세계는 애초에 온톨로지가 붙잡아야 할 중심축 자체가 달랐다.

| 비교 항목 | 개인 지식 온톨로지 (`Vault OS`) | 코드 도메인 온톨로지 (`Repo Ontology`) |
| :--- | :--- | :--- |
| **도메인 대상** | 생각, 학습, 의사결정 기록 (`Markdown`) | 소프트웨어 시스템, DB 제약, API, 소스 코드 |
| **주된 관심사** | **명사 (Taxonomy, 개념 분류와 계보)** | **동사 (Action & State Transition, 상태 전이)** |
| **핵심 질문** | "이 주장은 참인가, 선행 개념은 무엇인가?" | "이 상태에서 수납을 취소할 수 있는가? 어떤 행을 잠가야 하는가?" |
| **오류의 대가** | 지식의 고립, 검색 비효율 | 멀티 테넌트 데이터 유출, 동시성 충돌, 프로덕션 장애 |
| **최종 산출물** | 읽기 쉬운 정본 마크다운 문서 | 결함 없고 회귀 없는 실행 가능한 코드 |

당시 내가 홀로 설계하고 운영하던 B2B 학원 통합 관리 SaaS는 58개 화면 규모의 앱과 `FastAPI` 백엔드, `React`, `Flutter`가 얽힌 약 39만 줄 규모의 코드베이스였다. 흔히 개발자들은 데이터베이스의 ERD나 ORM 모델 정의서만 있으면 도메인을 다 파악할 수 있다고 생각하지만, ERD가 보여주는 테이블과 컬럼은 어디까지나 시스템의 정적인 뼈대, 즉 **'명사'**일 뿐이다.

실제 프로덕션에서 장애가 터지는 지점은 명사가 아니라 언제나 **'동사(상태 변경)'**에 있었다. 예컨대 "강사가 학생의 과제 제출물을 채점한다(`GradeSubmission`)", "수강생을 반에 배정한다(`EnrollCourse`)", "폐강 시 수납 상태를 전이한다" 같은 행위가 일어날 때, 어떤 권한(`role:instructor`)을 검증해야 하는지, 대상 엔티티가 어떤 사전 상태(`SUBMITTED` 또는 `RESUBMITTED`)에 있어야만 전이가 허용되는지, 동시 요청이 들어올 때 어느 테이블의 행을 잠가야(`SELECT FOR UPDATE`) 하는지 같은 핵심 불변식들은 ERD 어디에도 적혀 있지 않았다. 그 규칙들은 백엔드 서비스 코드와 API 라우터, 프론트엔드 컴포넌트 곳곳에 암묵적인 코드로 흩어져 있었고, 매 세션 기억이 초기화된 채 투입되는 AI 에이전트가 테이블 구조(명사)만 보고 코드를 고치다가 기존 비즈니스 불변식(동사)을 깨뜨리는 것은 어쩌면 너무나 당연한 귀결이었다.

## 에이전트 교차 검증: 엔지니어링 정직성 (`Antigravity` vs `Codex`)

이 지점에서 나는 팔란티어의 운영 온톨로지 개념을 내 코드 레포지토리에 본격적으로 이식하기에 앞서, 한 가지 중요한 자기 검증 과정을 거쳤다. 내가 구상하는 '코드 레포지토리 온톨로지'가 과연 팔란티어가 말하는 온톨로지 기준에 비추어 볼 때 어느 정도의 수준이며, 무엇이 같고 무엇이 다른지를 두 개의 독립적인 AI 에이전트(`Antigravity`와 `Codex`)에게 실제 로컬 코드베이스를 주고 냉정하게 교차 평가하도록 시킨 것이다.

결과는 매우 흥미로웠다. 첫 번째 에이전트였던 `Antigravity`는 내 설계가 팔란티어 AIP의 실행형 3단계에 도달했다며 후한 점수를 준 반면, 두 번째 에이전트인 `Codex`는 실제 코드 구현체를 샅샅이 뜯어보더니 아주 날카로운 실측 지적을 내놓았다.

| 분석 축 | `Antigravity` 관점 | `Codex` 실측 관점 | 최종 수용한 엔지니어링 판정 |
| :--- | :--- | :--- | :--- |
| **온톨로지 명칭의 정당성** | 정당함 (지식 및 코드 도메인 온톨로지) | 정당함 (도메인 명세와 관계 모델 근거 충분) | **O (공통 승인)**: 두 시스템 모두 온톨로지 개념을 정당하게 구현함 |
| **`Vault Ontology` 판정** | 지식 거버넌스 2.5단계 (Data + Logic) | 개인 지식 온톨로지 (`vault new` 생성 게이트 포함) | **O (일치)**: 지식 산출물 대상의 스키마 및 생성 거버넌스 |
| **`Repo Ontology` 판정** | AIP 실행형 3단계 완전 도달 | 코드에 연결된 도메인 온톨로지 명세 (런타임 실행 엔진 아님) | **시각 보정**: 런타임 트랜잭션 엔진과 SDLC 접지 명세의 엄격한 분리 |

`Codex`가 짚어낸 핵심은 명확했다. 팔란티어의 `Action Layer`는 현업 실무자가 버튼을 누르거나 AI가 도구를 호출했을 때 실제 기업의 ERP나 데이터베이스 트랜잭션을 직접 일으키는 **'런타임 비즈니스 실행 엔진'**이다. 반면 내가 코드 레포지토리에 구축하려는 시스템은 프로덕션 DB의 상태를 직접 변경하는 런타임 엔진이 아니라, 소프트웨어 개발 라이프사이클(SDLC)에서 코딩 에이전트가 코드를 수정하기 전에 반드시 읽고 준수해야 할 비즈니스 동사와 불변식, 그리고 실제 소스 코드의 위치를 1:1로 묶어주는 **'코드에 연결된 도메인 온톨로지 명세(Code-bound Domain Ontology Specification)'**라는 지적이었다.

나는 이 날카로운 지적을 기꺼이 수용했다. 엔지니어링에서 가장 경계해야 할 태도는 내가 만든 시스템을 실제보다 부풀려 마케팅 용어로 포장하는 일이다. 나는 "1인 개발자가 팔란티어 Foundry와 똑같은 전사 런타임 엔진을 만들었다"고 과장하는 대신, **"팔란티어 온톨로지의 4대 핵심(`Objects`, `Links`, `Actions`, `Invariants`) 철학을 소프트웨어 개발 라이프사이클(SDLC)이라는 특수 도메인에 이식하여, 기억상실증 코딩 에이전트의 코드 파괴를 막는 가장 단단한 하네스를 구축했다"**는 담백하고 정직한 포지셔닝을 내 시스템의 정체성으로 삼았다. 온톨로지는 엄격한 계약과 사전 불변식(`Spec & Invariants`)을 제공하고, 실제 코드를 고치고 검증하는 실행(`Action`)은 그 계약을 주입받은 에이전트와 자동화된 테스트 파이프라인(`TDD`, `Playwright`)이 수행하도록 역할을 명확히 분리한 것이다.

## 결핍에서 설계로: 무엇을 만들 것인가

정체성과 경계를 명확히 세우고 나니, 이제 코드 레포지토리 안에 구체적으로 무엇을 구축해야 할지가 손에 잡히듯 선명해졌다. 기존에 내가 [AI OS 시리즈 6편](/tag-ai-agent-architecture/6-repo-governance/)에서 구축했던 수기 운영 대장(`WORKLOG.md`, `docs/features/` 등)의 동기화 피로를 넘어, 에이전트와 코드베이스를 하나로 묶어줄 새로운 레포지토리 온톨로지 시스템(`otlg`)의 설계 목표는 크게 세 가지로 압축되었다.

첫째는 **4대 프리미티브(`Objects`, `Links`, `Actions`, `Functions`)의 표준 YAML 스펙화**다. 프로젝트 루트의 `.ontology/` 디렉토리 아래에 비즈니스 엔티티를 뜻하는 명사(`Objects`, `Links`)뿐만 아니라, 시스템의 상태를 전이시키는 동사(`Actions`)와 상태 변경 없이 순수 계산이나 AI 추론을 수행하는 함수(`Functions`)를 기계 가독형 YAML로 분리 선언하는 것이다. 특히 `Actions` 명세 안에는 누가 실행할 수 있는지(`actor`), 실행 전 어떤 조건이 참이어야 하는지(`preconditions`), 그리고 실행 후 어떤 상태가 변하고 어떤 이벤트가 발생하는지(`effects`)를 명시해 도메인 불변식을 한눈에 파악할 수 있게 해야 했다.

둘째는 **문서와 실제 소스 코드 간의 1:1 심볼 바인딩(`code_binding`)**이다. 아무리 훌륭한 온톨로지 명세서를 적어두어도 실제 코드가 수정될 때 문서가 따로 놀면 또 다른 쓰레기가 된다. 따라서 각 객체와 액션 명세 안에 백엔드 모델과 서비스 함수(`backend/app/services/...:grade_submission`), API 엔드포인트, 프론트엔드 피처 디렉토리, 모바일 뷰모델의 실제 파일 경로와 심볼 이름을 1:1로 바인딩하고, 정적 린터(`otlg lint`)가 실제 코드에 해당 심볼과 에러 메시지가 존재하는지 CI 단계에서 강제 검증하도록 설계했다.

셋째는 **0.01초 만의 결정론적 컨텍스트 복원(`otlg trace`)**이다. 새로운 세션에서 깨어난 백지상태의 에이전트가 수만 줄의 코드를 헤매며 `grep`을 돌리는 대신, 단 한 줄의 역추적 명령어만 실행하면 수정 대상 도메인의 모든 객체, 연관 액션, 사전 불변식, 그리고 건드려야 할 풀스택 파일 지도를 0.01초 만에 뇌에 주입받는 메커니즘을 구현하는 것이었다.
