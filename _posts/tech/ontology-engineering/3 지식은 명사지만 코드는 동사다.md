> 1인 개발자가 지식 온톨로지에서 코드 레포지토리 전용 실행 온톨로지로 도약하게 된 패러다임 전환의 뼈대.

## 1. 자만: "나는 이미 온톨로지를 정복했다"

- **[배경과 성취감]**
  - 볼트 4,400개 문서에 13개 엄격한 `type` 부여, `builds_on`과 7대 의미 관계로 완벽한 지식망 구축.
  - `vault new` CLI 생성 게이트와 `vault lint` 0건 무결점 달성.
- **[서술 포인트 / 말맛 가이드]**
  - 그래프 뷰에서 질서정연하게 얽힌 지식의 성채를 보며 "온톨로지를 소프트웨어 공학적으로 가장 우아하게 다루었다"고 착각했던 기술적 오만 솔직하게 고백.
  - 그러나 이 완벽한 평온은 2026 스타트업 페스티벌 'Try Everything'의 팔란티어 키노트 세션을 마주한 순간 산산조각 났다.

## 2. 충격: 팔란티어 키노트가 던진 일갈 ("We hate dashboards")

- **[원천 사건: 라이브 프로덕션 시연의 충격]**
  - 팔란티어(Foundry / AIP) 엔지니어 Alex와 Rosa의 현장 라이브 세션.
  - 슬라이드 자료 대신 당일 아침에 빌드한 실제 기업 운영 환경을 시연하며 던진 핵심 일갈:
    > *"We hate dashboards. 이미 알고 있는 데이터를 예쁘게 모아서 보여주는 대시보드는 우리에게 무의미합니다. 중요한 것은 비즈니스 실체를 대변하는 **객체(Objects)**와, 실무자가 즉각 조치를 취할 수 있는 **행동(Actions)**, 그리고 이를 통제하는 **불변식(Invariants)**입니다."*
- **[뼈아픈 자각: 도서관 사서의 한계]**
  - 내가 볼트에서 세운 온톨로지는 냉정하게 말해 **"예쁜 대시보드이자 잘 정돈된 도서관 분류표(Taxonomy)"**에 불과했다.
  - "이 문서는 concept인가?", "무엇을 먼저 읽어야 하는가?"는 지식의 부패를 막는 데는 훌륭했지만, 실제 현실의 문제를 풀고 소프트웨어의 상태를 변경하는 **실행형 온톨로지(Actionable Ontology)**와는 거리가 멀었다.

## 3. 본질: 지식은 명사지만 코드는 동사다

- **[개념 대조표: Vault 지식 온톨로지 vs Repo 코드 도메인 온톨로지]**

| 비교 항목 | 개인 지식 온톨로지 (Vault OS) | 코드 도메인 온톨로지 (Repo Ontology) |
|:---|:---|:---|
| **도메인 대상** | 생각, 학습, 의사결정 기록 (Markdown) | 소프트웨어 시스템, DB 제약, API, 소스코드 |
| **주된 관심사** | **명사 (Taxonomy, 개념 분류와 계보)** | **동사 (Action & State Transition, 상태 전이)** |
| **핵심 질문** | "이 주장은 참인가, 선행 개념은 무엇인가?" | "이 상태에서 수납을 취소할 수 있는가? 어떤 행을 잠가야 하는가?" |
| **오류의 대가** | 지식의 고립, 검색 비효율 | 멀티테넌트 데이터 유출, 동시성 충돌, 프로덕션 장애 |
| **산출물** | 읽기 쉬운 정본 마크다운 문서 | 결함 없고 회귀 없는 실행 가능한 코드 |

- **[프로덕션 현장의 실측 문제: 39만 줄 코드베이스]**
  - B2B 학원 관리 SaaS(58개 화면 앱 + FastAPI 백엔드).
  - DB ERD(테이블)는 시스템의 뼈대(명사)만 보여줄 뿐.
  - "폐강 시 수납 상태 전이", "성적 입력 시 출결 불변식 교차 검증" 같은 진짜 핵심은 서비스, ORM, 컴포넌트 곳곳에 숨어 있음.
  - 기억상실증 에이전트가 ERD만 보고 코드를 짜다가 행 잠금(`SELECT FOR UPDATE`)을 누락하고 테넌트 격리를 깨뜨리는 근본 원인이 바로 **동사 명세의 부재**에 있었음을 규명.

## 4. 에이전트 교차 검증: 엔지니어링 정직성 (Antigravity vs Codex)

- **[독립 에이전트 교차 분석]** 팔란티어 기준과 내 시스템의 수준을 두 에이전트에게 냉정하게 채점하게 함.
- **[Codex의 날카로운 실측 지적과 기준 보정]**
  - 팔란티어 온톨로지: ERP, SCM의 상태를 직접 변경하는 '런타임 트랜잭션 폐루프 엔진'.
  - 토마토의 Repo Ontology: 코드를 직접 런타임에 실행하는 것이 아니라, 코드의 물리 상태를 설명하고 사전 불변식을 인출해 주는 **'검증 가능한 접지 명세(Grounding Specification)'**.
- **[엔지니어링 정직성의 수용]**
  - "우리가 팔란티어와 똑같은 전사 엔진을 만들었다"고 과장하지 않는다.
  - 대신 **"팔란티어 온톨로지의 4대 핵심(Objects, Links, Actions, Invariants) 철학을 소프트웨어 개발 라이프사이클(SDLC) 도메인에 이식하여, 에이전트의 코드 파괴를 막는 가장 단단한 하네스를 구축했다"**는 담백하고 강력한 포지셔닝 확립.

---

## 5. 결핍에서 설계로: 무엇을 만들 것인가 (3대 설계 목표)

- **1) 4대 프리미티브(Objects, Links, Actions, Functions)의 표준 YAML 스펙**
  - 도메인을 명사(객체·링크)와 동사(액션·함수)로 분리 선언.
- **2) 소스코드 1:1 심볼 바인딩**
  - 문서가 따로 놀지 않도록 백엔드 라우터, 서비스, 프론트 컴포넌트의 물리적 소스 경로와 심볼을 1:1로 매핑.
- **3) 0.01초 결정론적 컨텍스트 복원 (`otlg trace`)**
  - 세션이 바뀐 에이전트가 단 한 줄의 명령으로 대상 도메인의 모든 코드 지도와 사전 불변식을 즉각 주입받는 기작.
